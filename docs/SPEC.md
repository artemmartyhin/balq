# Техническая спецификация: локальный архив storage на BAL

Рабочее название: `balq` (BAL query).

Версия 0.2, август 2026. Изменения относительно 0.1 перечислены в разделе 17.
Отличия реализации от этого документа — в `DECISIONS.md` (он главнее там,
где они расходятся).

---

## 1. Что это

Библиотека, которая накапливает изменения storage выбранных контрактов из
Block-Level Access Lists (EIP-7928) в локальное хранилище и отдаёт
исторические чтения состояния на обычной full-ноде.

**Формулировка для README (честная):**

> Веди историю storage своих контрактов с момента установки. Любой слот на
> любом блоке — локально, на обычной full-ноде, с проверкой полноты против
> заголовка блока.

Не «archive-нода не нужна» без оговорок: см. раздел 4 про горизонт данных.

### Три обещания

1. **Полнота.** Если слот не пришёл в BAL — он не менялся. Не «вероятно», а по
   построению: BAL обязан быть полным и валидируется консенсусом через
   `block_access_list_hash` в заголовке.
2. **Проверяемость.** Каждое значение в хранилище проверено: либо против хеша
   BAL в заголовке, либо Merkle-доказательством против `stateRoot`. Значений
   «на слово RPC» в базе нет (единственное исключение — явно помеченный
   импорт, раздел 9).
3. **Определённость границ.** Ответ на запрос — либо значение, либо явная
   причина отсутствия. Никогда молчаливый ноль.

Любая фича, которая не усиливает одно из трёх, — вне скоупа.

### Корень доверия

Библиотека доверяет своей ноде **в одном вопросе: какой блок канонический.**
Всё остальное проверяется локально: `keccak(rlp(header)) == blockHash`,
`keccak(rlp(bal)) == header.block_access_list_hash`, Merkle-доказательства
против `header.stateRoot`.

### Что это НЕ

- Не индексатор событий. Индексаторы (Ponder, Envio, SQD, subgraph) пишут то,
  что контракт сообщил логами. Здесь пишется само состояние.
- Не эксплорер и не мониторинг-платформа.
- Не хостится как сервис: продажа ответов со своего сервера уничтожает
  обещание №2.
- Не содержит знаний о конкретных протоколах.

Появление `adapters/<protocol>.rs` означает, что концепция сломалась.

## 2. Позиционирование

Слой **ниже** индексатора, а не альтернатива ему.

| Вопрос | Отвечает |
|---|---|
| «что произошло» | индексатор событий (Ponder и др.) |
| «в каком состоянии контракт был на блоке N» | balq |

- события пишет автор контракта и рассказывает только то, что счёл нужным;
  storage не врёт, потому что это не отчётность, а само состояние
- индексатор воспроизводит математику протокола офчейн (и тихо расходится на
  округлениях); здесь производные значения читаются из слотов как есть
- новый вопрос к индексатору = новая схема + переиндексация; здесь = другой
  запрос по тем же сырым данным
- индексатор не может доказать, что провайдер отдал все логи; здесь полнота
  подписана заголовком

Для 80% задач событий достаточно, и там Ponder лучше по всем параметрам.
balq нужен там, где событий не хватает или им нельзя верить.

**Ход по дистрибуции:** стать источником исторических чтений для существующих
индексаторов (их хендлеры сейчас упираются в archive-ноду).

## 3. Контекст и допущения

- EIP-7928 в статусе Review, **не заморожен**. Структура BAL может измениться.
- Glamsterdam: публичный тестнет Platåberget с 17 августа 2026, мейннет
  ориентировочно Q4 2026.
- BAL кодируется RLP; в заголовке лежит `block_access_list_hash` =
  keccak256(RLP(BAL)).

Ключевые свойства BAL:

- содержит **пост-значения**, не пре-значения
- `account_changes` отсортирован по адресу; внутри — `storage_changes` по
  ключу слота; внутри слота — по `block_access_index`
- адреса без изменений присутствуют с пустыми списками
- no-op writes (SSTORE тем же значением) в `storage_changes` не попадают
- `storage_reads` содержит ключи прочитанных слотов **без значений**

## 4. Горизонт данных (центральное ограничение)

Full-нода хранит состояние на последние ~128 блоков. Из этого следует всё
поведение бутстрапа и догона.

### Основной режим: forward-only

Установил → следишь → история копится. Через год есть год истории, и все
чтения обслуживаются локально. Archive не нужна ни на одном шаге — при
непрерывной работе (см. `DECISIONS.md` про окно proof и простои).

### Догон прошлого

История до момента установки требует отдельного механизма (раздел 9).

**Это ограничение пишется в README первой строкой, а не в FAQ.**

## 6. Бутстрап

BAL несёт только пост-значения. Слот, не менявшийся с момента старта, в
хранилище отсутствует — это неотличимо от «слот никогда не существовал».

### Ранний бутстрап (во время sync)

Слот впервые появился в BAL блока `C` → **немедленно** запросить его значение
на `C-1`. При синхронизации в реальном времени `C-1` в окне состояния ноды
(если нода отдаёт proof не только на голове — см. `DECISIONS.md`). Даёт
пре-значение для интервала `[start, C)`.

### Ленивый бутстрап (при чтении)

Слот с момента `start_block` ни разу не появлялся в BAL → значит **не
менялся** → его значение на голове архива верно для всего диапазона.

### Механизм: `eth_getProof`, не `eth_getStorageAt`

`eth_getProof(addr, [slots], block)` + проверка Merkle-доказательства против
`header.stateRoot`. Доказательство корректно подтверждает и **отсутствие**
слота (нуль по построению, не по умолчанию).

### Пропускная способность

Все слоты одного адреса, впервые увиденные в одном блоке, — один вызов.
Ожидающие бутстрапа слоты имеют дедлайн — окно ноды; по истечении они
помечаются потерянными и чтения в `[start, C)` честно отказывают.

## 7. Архитектура

```
bal-source     трейт источника BAL + реализации
bal-codec      парсинг BAL + верификация хеша      не знает про Solidity
bal-archive    накопление, версионированные чтения не знает про типы
bal-layout     storage layout -> типизация          не знает про хранилище
bal-layout-fetch  резолв layout из сети             (не построен)
bal-cli        diff, verify, export
bal-node       napi-rs биндинги
```

### `bal-source`

```rust
pub trait BalSource {
    async fn head(&self) -> Result<u64>;
    async fn finalized(&self) -> Result<u64>;
    async fn block(&self, n: u64) -> Result<SourcedBlock>;
    async fn header(&self, n: u64) -> Result<Header>;
}
```

Реализации: JSON-RPC (есть), Engine API и in-process/ExEx (не построены).

### Границы

Жёсткие. `bal-codec` — единственное место, куда придёт изменение спеки 7928.
`bal-node` не содержит логики, только маршалинг.

### Поток данных

```
BalSource
  -> verify(keccak256(RLP(bal)) == header.block_access_list_hash)
  -> filter(watchlist)
  -> ранний бутстрап новых слотов (eth_getProof на C-1)
  -> apply -> KV (два индекса)
                -> storage_at(addr, slot, block)
                -> layout -> типизированное чтение
                -> diff / stream
```

## 8. Модель данных

Embedded ordered KV (`redb`).

### Основной индекс

```
ключ:     addr(20) || slot(32) || block(8, BE) || index(4, BE)
значение: provenance(1) || value(32)
```

Big-endian обязателен — от него зависит корректность лексикографического
порядка при seek. Суффикс `index` (uint32 по EIP) закладывается сразу.
По умолчанию пишется только последнее изменение блока с его реальным
`block_access_index`; полная внутриблочная детализация — опция при
создании архива.

**Историческое чтение:** seek на `(addr, slot, target_block, MAX)`, шаг
назад, проверка совпадения префикса `addr || slot`. Одна операция.

### Индекс по блокам

```
ключ:     addr(20) || block(8, BE) || slot(32)
значение: пусто
```

Без него `changed_slots`, `diff` и откат реорга требуют обхода всех слотов
контракта.

### Служебные пространства

`watch`, `head`, `blockhashes` (хеш + stateRoot от финализации до головы),
`bootstrap` (состояние по слоту), `pending` (индекс ожидающих), `schema_version`,
`full_detail`.

### Реорги

Номер блока в ключе → откат = обход индекса по блокам выше точки форка.
Глубина отслеживания хешей привязана к тегу `finalized`.

### Оценка размера

~66 байт ключ + 33 значение, плюс запись во втором индексе. Для десятка
активных контрактов за год — единицы гигабайт. Требует замера.

## 9. Догон прошлого

Строго опциональная подсистема, не построена.

- **A.** Перечитывание старых BAL — даёт все изменения, но не пре-значения
  до первого изменения каждого слота.
- **B.** Сдвиг точки старта через `eth_getProof` на archive-эндпоинте —
  проверяемо, разово.
- **C.** Backfill через трейсы — вне скоупа (непроверяемо).

## 10. bal-codec

Структуры по тексту EIP (`BlockAccessIndex` = uint32, все uint256 — минимальные
байты в RLP). Схема отделена от логики; нарушение порядка при декодировании =
невалидный BAL. Тесты на реальных блоках Platåberget.

## 11. bal-archive

```rust
impl Archive {
    pub fn open(path) -> Result<Self>;
    pub fn watch(&self, addr, from_block) -> Result<()>;
    pub fn unwatch(&self, addr) -> Result<()>;
    pub async fn sync(&self, source: &impl BalSource, state: Option<&dyn StateSource>) -> Result<SyncReport>;
    pub fn storage_at(&self, addr, slot, block) -> Result<StorageValue, NotAvailable>;
    pub fn history(&self, addr, slot, range) -> Result<Vec<HistoryEntry>, NotAvailable>;
    pub fn changed_slots(&self, addr, block) -> Result<Vec<B256>, NotAvailable>;
    pub async fn bootstrap_slot(&self, state, addr, slot) -> Result<()>;
    pub fn head(&self) -> Result<Option<(u64, B256)>>;
}

pub enum NotAvailable {
    NotWatched(Address),
    BeforeStart { requested, start },
    AfterHead { requested, head },
    NotSynced,
    InvalidRange { start, end },
    NotBootstrapped,
    BootstrapPending { first_seen },
    BootstrapLost { first_seen },
    Internal(String),
}
```

`NotAvailable` — реализация обещания №3. `storage_at` возвращает `Result`, не
`Option`: «нет данных» и «слот равен нулю» различимы на уровне типов.

### Режим отказа

При непройденной верификации `sync` останавливается с ошибкой. Опция
`allow_unverified` существует для отладки и помечает записи
`Provenance::Unverified`. Никогда не по умолчанию.

## 12. bal-layout

Источник — `storageLayout` из артефакта solc (не ABI).

Случаи: layout опубликован (есть); верифицирован без layout — рекомпиляция
(`bal-layout-fetch`, не построен); прокси EIP-1967 — история implementation
из собственного архива (резолвер не построен, слоты читаются); beacon-прокси —
`NotWatched(beacon)`; ERC-7201/Diamond — не построен; неверифицирован —
сырые слоты.

Умеет: плоские переменные, упакованные поля, динамические и фиксированные
массивы, маппинги (включая вложенные), структуры; обратное именование слота
для всего, кроме элементов маппингов (keccak необратим).

---

## 13. bal-node (napi-rs)

Пребилды под 5 платформ через GitHub Actions; async-методы → промисы;
`NotAvailable` → `NotAvailableError` с `.code`, **не `null`**; ноль логики.

## 14. bal-cli

```
balq probe   --rpc URL
balq watch   ADDR --from N
balq sync    --rpc URL [--follow] [--proof-window N]
balq get     ADDR --slot S --block N | --layout L.json --field PATH
balq diff    ADDR --from A --to B [--layout L.json]
balq history ADDR --slot S --range A..B
balq verify  --journal rows.jsonl
```

Строка `[raw]` в `diff` обязательна: инструмент показывает, чего не смог
расшифровать, а не прячет это.

## 15. Критерий готовности

**Проект не существует, пока не работает `balq verify`.** Отчёт содержит три
категории — `match / mismatch / not_available` с расшифровкой причин.
Истина без archive-ноды: собственный контракт (`testbed/`) или контракты,
чьё состояние вычислимо из заголовков (EIP-2935).

---

## 16. Нефункциональные требования

- sync успевает за блоками с запасом; память — один BAL за раз
- историческое чтение — одна операция seek
- отсутствие паник в публичном API, все ошибки типизированы
- MSRV зафиксирован и проверяется в CI
